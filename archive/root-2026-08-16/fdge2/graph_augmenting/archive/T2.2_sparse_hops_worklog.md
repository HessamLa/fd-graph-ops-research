## Design decision: bounded-hop-radius BFS (NOT kNN)
The force law is shell-averaged: each node's contribution is averaged over
complete shells S_h(u) grouped by hop distance. Two candidate sparse
policies:

- **Bounded-radius BFS** (chosen): keep D[u,v] for all v within `radius`
  hops, drop the rest. Keeps every retained shell *complete*, so
  |S_h(u)| for h<=radius stays exact -> retained physics unchanged, only
  the far tail dropped. Sparse: ~(1+d+...+d^radius) entries per node,
  independent of n -> O(n) at fixed radius+degree.
- **kNN by hop distance** (rejected): hop distance is heavily tied (a whole
  shell shares one distance), so "k nearest" cuts *through* a shell,
  keeping an arbitrary subset. That corrupts the |S_h(u)| denominator the
  shell-averaging divides by. Wrong first policy for THIS physics. (kNN
  would fit a force law defined on a continuous feature distance -- not
  this shell-structured one.)

So: truncate *radius* (whole shells kept/dropped), never truncate *within*
a shell.

## Semantic choice: no `unreachable` sentinel
Hop-fill stamps disconnected pairs with a sentinel (default `n`). In the
sparse policy, "beyond radius" and "different component" are both just
**absent** (structural zero, not stored). The embedding stage treats both
identically (no attraction edge), so distinguishing them is exactly the
O(n^2) information a sparse policy declines to keep. Documented in the
module docstring.

## Implementation notes / gotchas
- `_bounded_hops_csr` (numba njit): two passes (count rows -> build indptr
  -> fill), so the output CSR is sized exactly and no (n,n) matrix is ever
  materialized.
- CRITICAL detail for sub-quadratic-ness: the length-n `dist` scratch is
  reused across sources and reset touching **only visited entries** after
  each source. A naive `dist.fill(-1)` per source would be O(n) per source
  = O(n^2) total and would silently defeat the whole point. Comment left
  in the kernel about this.
- Kept it single-threaded (no `prange`): a per-source prange needs
  per-thread size-n scratch, and the simple "allocate dist inside the loop"
  fix is O(n) alloc per source = O(n^2). Single-threaded + reset-visited is
  cleanly O(n + nnz). Fast enough (8000 nodes in ~0.1s); parallelization
  noted as possible-but-omitted (research code: fast to modify > fast to
  run).
- `D.sort_indices()` for canonical per-row column order (tidy `[i,j]`).
- Explicit diagonal: D[u,u]=0 is a *stored* entry (like hop-fill). Means
  "value 0" is ambiguous with "absent" at the Python `[i,j]` level, so the
  smoke test proves absence via the CSR structure
  (`_is_stored`), not via `D[i,j]==0`.

## Q4 (repulsion collapse) -- what I did
- Did NOT modify embedding/ (owned by another agent, out of scope).
- Demonstrated the risk is real:
  `test_collapse_risk_is_real` shows a far pair (path nodes 0 and 9 at
  radius 2) absent from D -> invisible to a force law that iterates D's
  row support -> zero repulsion even if they drift close in Z.
- Proposed a concrete, contract-preserving mitigation in the module
  docstring's delimited "Q4 mitigation proposal" section: **sampled
  negatives** -- per row, draw m random node ids (n = D.shape[0]), add a
  1/m-scaled repulsion term reusing the existing `_scalar_force` repulsive
  branch. Plugs in through `forces`'s existing `**kwargs` (`neg_samples=m`)
  + `self.rng`; needs no new positional arg and no missing-pair data;
  stays row-streamed O((rows)*d + m*d). Secondary option (wider repulsion
  radius via a second pattern) noted but flagged as still-bounded, so it
  doesn't cover the truly-far tail; sampled negatives do.

## Scaling measurement (archive/bench_sparse_hops_scaling.py)
Erdos-Renyi, avg_degree=8, seed=0, radius=2:

| n    | sparse_nnz | nnz/n | sparse/n^2 |
|------|-----------|-------|-----------|
| 500  | 34134     | 68.3  | 0.1365    |
| 2000 | 143552    | 71.8  | 0.0359    |
| 8000 | 582388    | 72.8  | 0.0091    |

nnz/n stays flat (68->73, spread 1.07x) across a 16x increase in n =>
O(n), not O(n^2). sparse/n^2 falls 0.14 -> 0.009 as n grows (pulling away
from dense). Head-to-head vs dense hopfill at r=2: 7.3x fewer stored
entries at n=500, 27.9x fewer at n=2000 -- the reduction factor GROWS with
n, the signature of O(n) vs O(n^2). radius=3 is denser (nnz/n ~320-560,
spread ~1.7x as d^3 neighborhoods start saturating at this size) but still
far below n^2 (ratio 0.65 -> 0.07, dropping).
