## 2026-08-17T22:40 -- the plane count of fdlinear

**The question.** The user observes that `h` (from `D`) and `freq` (from
the coefficient matrix) meet in one place only, the repulsion, and
proposes: (1) one CSR whose data entry is `[h, freq]`; (2) one resident

**What I measured first.** At `n = 1,134,890`, `nnz = 23,163,843`,
`pad_frac = 0.154`, thus 27.38 M padded slots. One plane costs 92.7 MB as a
host array and 109.5 MB as a packed tile.

**Finding 1, and it is larger than either proposal.** `fdlinear` binds
`_shell` and never reads it, but `augment_graph` built it for every run.
`shell_coeff_data` calls `shell_counts`, `row_of`, and a `searchsorted`,
two of which are nnz-sized int64: about **460 MB of transient**, for a
92.7 MB array and a 109.5 MB tile that the kernel drops. This is a defect
of my own, from the day `fdlinear` was written.

**Finding 2. Proposal (1) is already the design.** `make_plan` takes planes
that are aligned 1:1 with `D.indices`; there is no second index structure
at the plane level, and the bench uses `stats["freq"].data` only. The waste
is that `to_csr_directed` builds a whole CSR to get the alignment, and the
indices are then dropped: 97 MB. Real, but the smallest of the three.
(A scipy `csr_matrix` cannot hold an `(nnz, 2)` data array; two aligned 1-D
arrays IS the representation the proposal describes.)

**Finding 3. Proposal (2) is correct, and as written it breaks the law.**
`h` has three uses, not one: `live = h > 0`, `near = h <= 1`, and
`h / freq`. With `w = h / freq` the pad mask survives, but the BRANCH does
not: `h=1, freq=3` and `h=2, freq=6` both give 0.333. The attraction would
fire on the wrong cells, and nothing would raise an error.

**The fix, and why it is free.** The `h == 1` branch reads neither `h` nor
`freq`; its coefficient is the constant `kr`. Thus it needs a FLAG and no
value, and the sign carries the flag:

```
w = -1.0      h == 1     (sentinel)
w = h / freq  h >= 2     (always > 0)
w = 0.0       pad
```

Three disjoint regions. `degrees_from_D` counts the `h == 1` entries, thus
it must be read BEFORE the collapse, and the bench does that.

**The cost of fusing, stated before it is adopted.** `h / freq` becomes a
build-time quantity. `k1`, `k4`, `kr` stay traced and sweep for free, but a
law of the form `h / freq**beta` could not sweep `beta` without a rebuild
of `D`. Thus fusing is a flag now, and a default only when the law stops
moving.

### 1. The optimizer roster (`optim.py`)

## 2026-08-18T01:50 -- `shell_anneal` added to the roster

**Instruction.** A gradient update schedule: begin with every `h=1` and
`h=2` pair plus a random subset of longer pairs sampled each epoch, and
shift the mixture toward the long pairs as the embedding proceeds. Expected
lower memory and runtime with small changes elsewhere. The user asks for
the best title.

**The name I gave it: `shell_anneal`.** `shell` is already the project's
word for the level set `S_h(u)`, thus the name says what is scheduled in
vocabulary the code owns. `anneal` is the standard word for a monotone
per-epoch schedule and force-directed layout carries that tradition from
Fruchterman-Reingold. The runner-up was `expanding_horizon`, rejected
because it invents a word where `shell` already exists.

**Three traps found while writing the item, and the first one is fatal to
the method as stated.**

1. **The attraction lives ONLY at `h = 1`.** `shell_force` multiplies `Fa`
   by `guard = where(h > 1, 0, 1)`, and `fdlinear` gates `Fa` on
   `near = h <= 1`. A schedule that lets the LOCAL share fall to zero
   removes all attraction and the layout expands without a limit. Worse, it
   fails silently: `degrees_from_D` counts the `h == 1` entries, a row that
   loses them gets degree 0, `inv_deg_ext` makes that 0.0, and the kernel
   zeroes the WHOLE row force -- the node freezes and nothing errors. This
   is the identical trap `low_deg` hit on 2026-08-17. **The item therefore
   anneals `h >= 2` only, and `h = 1` stays resident for every epoch.**
2. **"all h=2" must mean the WALK GAP and not the true 2-hop ball.** The
   true 2-ball is the abandoned k-ball policy: 2.5 G pairs and 50 GB on
   com_youtube. The walk gap is bounded by `n_walks * walk_len` and is a
   subset of it. The item is feasible only under the walk-gap reading.
3. **The memory and runtime claims need a specific implementation.**
   Resampling long pairs changes the sparsity pattern, and the
   SELL-C-sigma plan bakes in the neighbour indices, thus a naive form
   REBUILDS the plan every epoch and would raise the runtime rather than
   lower it. The form that can deliver both claims: one plan, built with
   the resident `h <= 2` pairs plus a FIXED slot budget for the long pairs,
   refilling only those slots each epoch -- same nnz, same tiles, no
   replanning. And the long set must never be materialised in full, because
   freeing does not lower a high-water RSS.

## 2026-08-18T02:05 -- renamed to `edge_sampling`, and the budget resolves trap 3

**Instruction.** "forget about shell. this is not shell anymore. we have
diverged from it by miles. this is walk based. fdwalk. ... in the suggested
method, the schedule for edge set changes. we might want to respect an
allowed number of edges for each set to follow the sell-c-sigma memory
optimization. 'edge sampling during embedding'"

**The rename, and why my first name was wrong.** I proposed `shell_anneal`
on the argument that `shell` is the project's vocabulary. The rejection is
correct and I record the reason rather than only the change: `h` in fdwalk
is a WALK GAP and not a shell index, and `fdlinear` reads no `shell_coeff`
at all -- I REMOVED that plane on 2026-08-17 because the law never used it.
Naming a new method after a quantity the current force law does not have
would point at the abandoned formulation. `edge_sampling` also says the one
thing that distinguishes it: every policy of this branch so far (`cap`,
`buckets`, `low_deg`, `row_cap`) decides the edge set ONCE, before the
first epoch; this one decides it again at every epoch.

**The per-band budget requirement resolves trap 3 instead of avoiding it.**
I had written that a naive form rebuilds the plan each epoch and would
RAISE the runtime. A fixed edge budget per set removes that, because the
plan geometry stops depending on the sample.

**But the budget collides with trap 1, and the collision has to be designed
out.** Trap 1: every `h = 1` entry stays resident. A fixed row width `m`:
a com_youtube hub has degree 28,754, and no useful `m` holds it. Both
requirements are right, thus neither can be dropped.

**The resolution: two plans, both built one time.**

    D_near     every h = 1 pair, resident, never resampled.
               5,975,248 entries at 1.13M -- the adjacency, the cheap part.
    D_sampled  exactly `m` slots for each row, refilled each epoch from the
               h >= 2 pairs. Exactly `n * m` entries by construction.
    dZ = dZ_near + dZ_sampled

Both geometries are FIXED, thus neither plan is rebuilt: only the `nbrs`
and the plane values of `D_sampled` change, and their shapes do not. The
split is exact because the force law is a SUM over the stored pairs of a
row -- the same property that permits the chunking of axis D1.

Arithmetic at 1.13M, `m = 8`: `5,975,248 + 1,134,890*8 = 15,054,368`
entries against 23,163,843 today, a fall of 35%. The point is not the 35%:
it is that **the `h >= 2` set is never materialised in full**, and only
memory never allocated lowers a high-water RSS.

`row_cap` already measures the SELL-C-sigma half of the claim: a cap of `m`
gives a maximum row width of exactly `m` and exactly `n*m` entries. Thus
`D_sampled` should show `n_split = 0` and `pad_frac` near 0, against 0.154
today, and that is now an explicit item -- if it does not happen, the
optimisation is not being taken.

One consequence carried into the item: with two matrices the force-law
degree must come from `A`. `--deg-source A` already does this and exists
for the `low_deg` trap; reuse it rather than re-deriving it.
